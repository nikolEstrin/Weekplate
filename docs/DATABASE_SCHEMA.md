# Database schema

Two databases hold the same domain model: Postgres in Supabase (durable, cross-device)
and SQLite on the device (what the app reads). Rows keep the same keys in both, so
sync never translates IDs. Binding rules live in [DATA_CONTRACT.md](DATA_CONTRACT.md).

## Domain aggregates

| Aggregate | Cloud table | SQLite table | Key | Children stored as JSON |
|---|---|---|---|---|
| Shared starter catalog | `global_products` | `global_products` | `id` | `units` |
| Private product / override / hidden marker | `products` | `products` | `(user_id, id)` / `id` | `units: [{id, name, grams}]` |
| Meal (recipe) | `meals` | `meals` | `(user_id, id)` / `id` | `ingredients`, `tags` |
| Day plan (day/week/month planning) | `day_plans` | `day_plans` | `(user_id, date_key)` / `date_key` | `slots: {breakfast, lunch, dinner, snacks}` of planned-item snapshots |
| Goals | `user_settings` | `user_settings` (single row, `id = 1`) | `user_id` / `1` | – |
| Shopping list checks | `shopping_checks` | `shopping_checks` | `(user_id, selection_key)` / `selection_key` | `checked: {itemId: true}` |

Units, ingredients and plan slots are JSON inside their parent because the UI
always edits them together with the parent. That makes every sync write atomic
and avoids child-row ordering and foreign-key failures between offline devices.
Relationships inside JSON use stable IDs, never names:

- meal ingredient → `productId` (+ optional `unitId`) or nested `mealId` (depth ≤ 3, no cycles; enforced by `storage.js`)
- planned item → `sourceMealId` and product IDs, plus a nutrition snapshot so a plan survives product deletion
- shopping item ID → `productId::unitKey`

Weeks and months are not stored separately: they are ranges of `day_plans` dates
(weeks start on Sunday).

## Global vs private products

- `global_products` is seeded from `src/data/starterProducts.json` (54 products, fixed
  product and unit IDs) by migration `20260925151000_seed_global_products.sql`
  (`insert … on conflict (id) do update`, idempotent). Users can only read it.
- Editing a starter product creates a private `products` row **with the same id**
  (an override). Deleting a starter creates a private row with that id and
  `deleted_at` set (hidden for this user only). Global rows are never modified by users.
- Effective catalog on the device = live globals in `sort_order`, each replaced by its
  override or dropped if hidden, followed by private products ordered by `created_at, id`.

## Cloud (Postgres)

Migrations: `supabase/migrations/`

1. `20260925150000_create_sync_schema.sql` — tables, CHECK constraints, triggers, indexes, RLS, grants.
2. `20260925151000_seed_global_products.sql` — generated by `node scripts/generate-global-products-seed.mjs`.
   When the starter JSON changes, generate a **new** migration file rather than editing an applied one.

Common private-table columns: `user_id uuid references auth.users on delete cascade`,
`updated_at` (client logical time, the LWW key), `created_at`, `server_updated_at`
(pull cursor), and `deleted_at` (tombstone; not on `user_settings`).

Constraints: nutrition values ≥ 0; overage 0–500; live rows need a non-blank name;
meal tags ⊆ {breakfast, lunch, dinner, snack, dessert}; JSON type checks
(`units`/`ingredients` arrays, `slots` object containing the four slot arrays).

Triggers (`set_private_sync_metadata`, `search_path = ''`):
- insert: `user_id := auth.uid()` (error if not signed in), keep client `created_at`, clamp `updated_at` to ≤ now + 5 min, set `server_updated_at`.
- update: `user_id` and `created_at` immutable, clamp, **skip the update if `updated_at` is older than the stored value**, set `server_updated_at`.

Row Level Security is enabled on all six tables:
- private tables: SELECT/INSERT/UPDATE/DELETE `to authenticated` with `(select auth.uid()) = user_id`;
- `global_products`: SELECT `to authenticated` only; no write privileges granted;
- `anon` has no privileges on any table.

Indexes: `(user_id, server_updated_at)` on each private table; `global_products(server_updated_at)`.

Account deletion: Edge Function `supabase/functions/delete-account` deletes the auth user; the FK cascade removes every private row.

## Device (SQLite)

File per user: `weekplate_<userId>` (in `Library/CapacitorDatabase` on iOS). Migrations
in `src/db/migrations.js`, versioned with `PRAGMA user_version`, each applied in a
transaction. Upgrades only add; they never drop user data.

Version 1 tables: `meta` (user id, sync cursors `cursor:<table>`, `legacy_import_v1`),
`global_products`, `products`, `meals`, `day_plans`, `user_settings`, `shopping_checks`
(JSON stored as TEXT; each synced table has `created_at`, `updated_at`, `deleted_at`,
`server_updated_at`, `sync_status` = `pending`|`synced`), and `sync_queue`
(`entity_type`, `entity_id`, `operation`, `attempt_count`, `last_error`,
`next_attempt_at`, `UNIQUE(entity_type, entity_id)`).

Indexes: `sync_queue(next_attempt_at)`, `products(deleted_at)`, `meals(deleted_at)`.

To add a local schema change: append `{ version: 2, statements: [...] }` to
`migrations` in `src/db/migrations.js` and add a test that opens a version-1
database and upgrades it.
